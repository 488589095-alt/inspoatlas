## 1. 产品定位与不可改变的边界

InspoAtlas 面向 UI、产品与视觉设计人员。它不是 Stitch/Lovart 的替代品、通用白板、收藏夹或直接替用户出最终设计的生成画布。

产品任务是把图片、网页和文字参考转化为有来源、可确认、可复用的设计生产上下文：

`采集参考 → 拆解素材 → 整理关系 → 整合设计方案 → 按用途导出`

- **拆解**：将参考中的版式、色彩、间距、圆角、组件和内容层级转成结构化结果，并保留来源。
- **方案**：用户可选择多个拆解结果，合并其共同点，显式保留冲突和未确认项；它是一个可保存、可继续编辑的画布节点，不是隐藏在侧栏的一次性摘要。
- **导出**：按用户要做的事输出，不再给一个杂乱的通用 ZIP。
- **设计助手**：仅服务开放性的取舍、方向和解释，作为右下角悬浮入口；确定性的拆解、方案、导出仍以画布内流程完成。
- **连线**：仅辅助用户整理关系，默认不应抢占画布；用户可手动连线、编辑连线文字，且默认只显示当前选择相关的关系。

任何 AI 建议、自动整理或未来自动采集都必须可预览、可拒绝、可回到来源，不能静默改写用户画布。

## 3. 已实现能力（以代码为准）

### 画布与素材

- 多画布创建、切换、复制、删除、原位重命名；图片、网页、文字、备注、分组、分析与方案卡片。
- 上传多图片、文件夹、网页 URL、文字；网页卡片可分别滚动查看截屏和正文。
- WXT MV3 浏览器插件可将标题、URL、可读正文、关键样式和分段全页截图送入指定 `boardId`。
- 卡片拖拽、缩放、右键拖动画布（抓手光标）、Shift 多选、完整覆盖式框选、对齐、撤销/重做、分组、删除与备注。
- 分组标题和说明可直接编辑；AI 生成分组同样可被用户原位修改。
- 左右侧栏均有真正可拖动的宽度分隔条（双击恢复默认）；悬停颜色为紫色。
- 自动保存会合并临时选择等高频状态，配合本地草稿恢复和服务端版本冲突处理，不能改回每次交互都请求保存。
- 节点搜索支持关键词、类型筛选与点击定位；专注模式、缩略图及搜索联动存在，但需继续做真实浏览器视觉冒烟。

### 拆解、方案与导出

- 对真实图片/网页素材发起结构化拆解；未配置可用 Key 时诚实报错，不生成假结果。
- 拆解结果会作为来源卡片的可折叠内容，同时可成为独立“拆解结果”节点；同一素材重新拆解更新原结果，避免产生重复卡片。
- 从卡片端口或“下一步”菜单进入后续步骤；多个已完成拆解被多选时，可预览整合为一套设计方案。
- 方案包含设计原则、颜色/间距/圆角 Tokens、组件、冲突、未确认项及来源素材；用户可逐项点击 `×` 排除不采用的内容，确认后保存为方案卡并与来源连线。
- 方案数据层已保存颜色/组件/原则的来源素材 ID，导出的部分文件也会写出证据；**但当前方案弹窗尚未将每一项的来源做成可点击、可定位的交互**。这只是数据/导出层的半成品，不能对用户或简历声称已完成“可追溯来源引用”。
- 点击方案卡或其端口进入输出选择。输出应先选生产用途再选使用工具。
- 支持网页/UI 复刻、图片/品牌延展、批量活动页与 Figma 工作流等任务包；每包包含与用途相符的设计规则、提示词、Tokens、组件说明、来源映射与 QA。
- **Figma 快速路径**：下载 SVG，直接拖入 Figma 后编辑文字、色块和图形。
- **Figma 完整路径**：下载 `figma-import.json` 与本地开发插件，创建 Variables 和组件草稿。Figma 公共接口不能直接生成原生 `.fig` 文件，绝不能对用户宣称已支持。
- Figma Make 与 Figma Buzz 只输出对应的可执行指南/内容模板；Buzz 适合批量品牌物料，不适合复杂网页。`slots` 指模板的内容预留区域，用于限制标题、图片等可替换内容不破坏版式。

### 已确认的产品方向：按任务拆解，而非一套流程硬套所有需求（尚未完整实现）

当前 `analysisResultSchema` 是一套通用拆解结构，任务目的主要在方案/导出阶段才选择。这是可运行 MVP 的实现方式，但不应作为最终产品逻辑：网页复刻、图片提示词、品牌延展和批量活动页对“该拆什么、该由谁决策、该交付什么”的要求不同。

下一轮必须区分两个维度：

- **用户任务（Purpose）**：用户想完成什么工作。初步固定为：网页/UI 复刻、图片/品牌视觉延展、批量活动页系统；另保留“仅整理灵感”作为不强制进入 AI 生产的模式。
- **交付去向（Destination）**：用户要在哪里继续工作。包括 Coding AI、图片 AI、Figma SVG、Figma Plugin 导入、Figma Make、Figma Buzz。Figma 可编辑导入不是与“品牌延展”并列的用户任务，而是一个交付去向。

目标流程：

`采集参考 → 通用基础拆解 → 选择任务并填写最小目标 Brief → 任务专属候选池 → 用户采用/排除/仅参考 → AI 基于已选项撰写规范 → 选择交付去向并导出`

不要强制用户在上传前就选定任务；可在开始“整合为方案”时询问目标。基础拆解应可复用，用户改变目标时只切换任务视图，不能重复抓取或丢弃原始分析。

各任务的差异：

| 用户任务 | 最小 Brief | AI 拆解/候选重点 | 用户主要决策 | 典型交付 |
| --- | --- | --- | --- | --- |
| 网页/UI 复刻 | 要复刻的范围、平台/尺寸、保留与排除项 | 页面模块、布局、组件、交互状态、Tokens、响应式线索 | 哪些模块/组件复刻，哪些仅作参考 | 结构规范、组件说明、Coding AI 任务、Figma 画板 |
| 图片/品牌视觉延展 | 品牌/主体、使用场景、受众、必须保留/禁止项 | 构图、主体、色彩角色、材质、光线、排版/图形语言、负面约束 | 选择新品牌要继承的视觉字段，确认冲突取舍 | 品牌规范、图片提示词、受控变体、Figma 资产 |
| 批量活动页系统 | 页面数量、固定模块、可变内容、投放渠道 | 固定层、可变 Slot、组件矩阵、内容字段、变量规则 | 哪些规则锁定，哪些内容可替换 | 模板画板、Slot 规则、组件矩阵、内容表 |

Prompt 与 Schema 应采用“**基础层 + 任务扩展层**”，不能为每个任务复制一套互不兼容的数据结构：

- 基础层：素材 ID、候选字段、字段类别、原始值、置信度、来源素材 ID、状态。
- 网页/UI 扩展：模块、布局、组件、状态、Tokens。
- 品牌延展扩展：品牌气质、视觉原则、色彩角色、图像/材质/构图语言、禁止项。
- 活动页扩展：固定层、可变 Slot、组件矩阵、内容 Schema。

推荐的候选字段状态是：`待选择 / 采用 / 排除 / 仅参考`。AI 的职责是拆解、归类、相似项合并建议和冲突提示；AI 可以提供“推荐组合”，但不得静默删除候选或替用户作最终取舍。用户先筛选，AI 再只基于“采用”的字段生成可编辑规范。

品牌延展尤其不能采用“AI 先压缩为一套最终方案、用户被动删除”的模式。必须先保留灵感 A/B/C 的所有可用字段，展示字段的来源缩略图/卡片，再由用户决定是否把 A 的摄影氛围、B 的色彩、C 的排版共同组成新规范。

### AI 体验、质量与安全

- 用户界面固定显示并使用 **GPT-5.6 Terra**，拆解与设计助手共享模型；不要把内部 `managed/byok` 运行方式作为普通用户决策暴露。旧 Provider Adapter 和 BYOK 兼容逻辑仍在服务端，供部署/迁移使用。
- AI 输出经过 JSON 清洗、思考标签/代码围栏处理、常见简写归一化和 Schema 校验；失败保留旧结果并给出中文可操作原因。
- 每次拆解和助手调用记录模型、Prompt 版本、Schema 版本、运行方式与行为事件；结果可提交有用/不准确等质量反馈。
- 设计助手必须询问/引用设计目标和具体画布卡片，可将建议保存回画布，但不能替用户直接执行高影响动作。
- URL 输入会拦截危险协议和私网地址；Provider 端点有白名单；模型凭据加密保存。

## 6. 未完成项、已知风险与下一步

### 必须诚实保留的缺口

- 当前站点是私有线上演示，不是公域产品；公开前需要账号/权限、隐私与条款、配额限流、成本控制、内容治理、监控告警、版权投诉与真实用户支持能力。
- Figma Bridge 仅为开发导入方案，未达到可发布插件水平；不支持原生 `.fig` 导出或双向同步。
- 自动搜集灵感、登录态网页/复杂反爬抓取、实时协作、评论、移动端、订阅支付和素材社区均未完成。
- AI 尚无 30—50 条真实设计案例构成的黄金评测集；没有真实 Key 的情况下不得假装验证了图片或网页拆解质量。
- 多参考整合当前会去重并限制展示数量，存在候选被静默省略的风险；它不适合直接作为品牌延展的最终筛选方式。需要改为“保留全部候选字段 → 用户选择采用/排除 → AI 只基于已选项生成规范”，并将 AI 的归类、去重和冲突提示明确标记为建议。
- 来源追溯需要在方案卡/方案弹窗中补齐：每条原则、颜色、组件旁显示来源缩略图或数量，点击后高亮并定位到对应参考卡；用户才能真正审核 AI 的依据。
- 当前通用 Schema 和“导出时才选择用途”的流程，不足以覆盖不同任务。要引入 Purpose 与 Destination 两层模型、最小目标 Brief、基础 Schema 加任务扩展 Schema；这是已确认的优化方向，尚未落地，不可当作已实现能力。
- 500 节点性能、弱网恢复、分享撤销、跨账号权限、Figma 导入实物和所有新 UI 的真实浏览器手感仍需冒烟验证。

### 建议的下一轮优先级

1. 使用真实 OpenAI Key 做图片、网页拆解和设计助手冒烟，记录结构成功率、P95 延迟、费用与失败原因。
2. 在真实浏览器逐项验证近期交互：左右侧栏宽度是否真的变化、端口拖线能否成功、连线标签可否编辑、专注模式是否布局正常、缩放时背景点是否同步。
3. 在“整合为方案”前增加 Purpose 选择与最小目标 Brief，并将 Purpose（网页/UI 复刻、图片/品牌延展、批量活动页、仅整理）和 Destination（Figma/Coding AI/图片 AI/Figma Make/Buzz）从数据和界面上分离。
4. 以“基础 Schema + 任务扩展 Schema”重做候选池：先保留各参考的所有字段候选，再让用户筛选；AI 只做归类、相似项合并建议、冲突提示和基于已选项的规范撰写，不能静默丢弃候选。
5. 补齐方案逐项来源追溯：每个候选/规范项显示来源缩略图或数量，点击定位对应画布卡片，并让导出沿用同一证据映射。
6. 找 5—10 位目标用户做观察式可用性测试，重点看“参考 → 拆解 → 候选筛选 → 方案 → 导出”是否能独立完成。
7. 用真实成功/失败案例建立评测集；每次只改模型、Prompt、Schema 或交互中的一个主要变量，区分正式流量与兼容 BYOK 流量。
8. 用户确认后，再规划公开测试：先做受控公测和数据/成本/合规底座，不能直接把私有预览改为大规模开放。

## 7. 开发纪律

- 不覆盖既有用户改动，不使用 `git reset --hard` 或强制回退。
- 新功能先补最小测试；修改完成运行相关测试与生产构建。
- 不留下“按钮显示成功但数据未持久化”的假功能。
